02How it worksfour line-items
01Bind

Bind an agent that already exists.

Point an ENS name — agent.ops.acme.eth — at an external autonomous agent you already run. Its identity is on-chain-resolved through ERC-8004; LEASH binds the leash, it does not create the agent.

02Declare

Declare the spend policy on the name.

Write the policy into the ENS resolver record: a per-call ceiling, an allow-list of endpoints, and a rolling softBudget daily and weekly cap. The name itself carries the rule.

03Enforce

Enforce at every gas-free settlement.

A forked Hedera x402 facilitator — the facilitator we run — reads the ENS-declared policy before each settlement. Spend rides a 2-of-2 co-signed Hedera account (the agent holds one key, LEASH the other); neither spends alone. Privy is the independent second rail on the funding flow.

04Revoke

Revoke with one on-chain write.

Clear the resolver record — one write to leash.policy. The agent's next payment fails closed everywhere, and the co-signer stops counter-signing. No queue to drain, no keys to rotate.

03The honest versionread the fine print
What LEASH is, and what it is not. Expand ›
Model
A corporate-card model, not a trustless one. There is a party in the loop — you can see it, and you can cut it.
The chain
The chain stores the policy and records the revocation. The facilitator we run enforces the org's ENS-declared policy at settlement time.
Identity
Agent identity is on-chain-resolved through ERC-8004. That is a resolution, not a claim we call "verified."
Caps
Rolling daily and weekly caps are a soft budget — a rolling ceiling the facilitator holds to, not a limit the chain itself enforces.
Funding
Privy is the independent second rail on the funding flow, and it denies over-funding on that rail — a separate check from the spend policy.
Scope
LEASH binds agents. It does not create or mint them; it leashes agents that already exist.
